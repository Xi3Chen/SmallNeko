# SmallNeko 学习与实验计划

## 1. 项目愿景

SmallNeko 用于学习前沿语言模型技术，并验证一种与“扩大知识规模”不同的路线：

> 在知识量和参数量都有限的情况下，通过更充分的内部计算、结构化的记忆访问、外部检索和结果验证，让模型解决复杂问题的能力超过同规模的普通模型。

这里的“更聪明”主要指：

- 能够分解问题并制定解决步骤；
- 能够组合相距较远、关联较弱的知识点；
- 能够在多轮计算中修正早期错误；
- 能够调用资料、代码或规则验证器；
- 能够区分“我知道”“我推测”和“我无法确认”。

项目不追求让模型在所有领域都博学，也不把自然语言表达的丰富程度作为首要目标。更接近的目标是一个知识覆盖有限、逻辑推理和问题求解能力较强的系统，可以理解为“左脑能力较强、右脑能力较弱”的 AI。这里的“左脑”和“右脑”只是能力侧重点的比喻，不对应真实的大脑结构。

## 2. 研究假设

项目围绕以下假设展开：

1. 小模型的能力上限不完全由参数量决定，测试时增加有效计算可能提升复杂任务表现。
2. 共享权重的循环模块可以让模型用较少参数执行更多轮计算。
3. 注意力残差或历史状态读取可以帮助循环模块重新访问早期信息，减少中间推理结果丢失。
4. Mamba 可以作为高效的序列建模组件，降低部分长序列处理成本。
5. 搜索算法可以帮助模型在多个推理、检索和工具调用路径中选择更好的路径。
6. 搜索只有在存在可靠的评分器或验证器时才有价值；否则它可能只是更昂贵地重复错误。

这些假设必须通过对照实验验证，不能因为某个模型生成的样例更好就直接得出结论。

## 3. 技术分层

项目中的技术属于不同层次，应分别研究：

| 层次 | 技术 | 作用 |
| --- | --- | --- |
| 知识来源 | 训练数据、文档检索、工具调用 | 提供模型原本没有的事实或材料 |
| 训练目标 | 自回归、扩散式去噪 | 决定模型如何学习生成和修正序列 |
| 序列骨干 | Transformer、Mamba、混合结构 | 处理 token 之间的信息关系 |
| 内部计算 | Looped Transformer、共享权重循环 | 对同一个问题执行多轮计算 |
| 状态访问 | 普通残差、注意力残差、外部记忆 | 保存并读取早期中间结果 |
| 结果评估 | 规则验证器、执行器、奖励模型 | 判断候选答案是否正确或更有希望 |
| 测试时搜索 | Best-of-N、束搜索、MCTS | 在多个候选解或行动路径中进行选择 |

Mamba、Looped Transformer 和 MCTS 中都可以看到“循环”，但它们不是同一种循环：

- Mamba 沿 token 方向递推序列状态；
- Looped Transformer 在深度方向重复执行模块；
- 扩散模型在噪声状态和干净状态之间逐步去噪；
- MCTS 在问题状态组成的树上扩展、评估和回溯。

它们可以组合，但每增加一种循环，计算成本、训练难度和错误来源都会增加。实验必须逐层加入机制。

## 4. MCTS 能解决什么问题

MCTS 适合搜索“解决问题的路径”，不负责凭空创造知识。它特别适合以下场景：

- 一个问题可以拆分成多个行动或子问题；
- 每个行动会产生一个新的可描述状态；
- 可以通过检索、代码执行、规则检查或奖励模型评价状态；
- 错误路径可以被提前淘汰，较好的路径可以继续扩展。

例如，对于一个跨领域问题，搜索节点可以表示：

```text
当前问题状态
  -> 选择需要确认的概念
  -> 检索相关材料
  -> 建立两个领域之间的关系
  -> 寻找反例
  -> 使用验证器检查结论
  -> 生成最终答案
```

MCTS 不能解决以下问题：

- 基础模型和检索库都没有相关知识；
- 没有办法判断一个中间结论是否可靠；
- 搜索动作无法产生新的有用状态；
- 评分器只偏好语言流畅度，而不能判断事实或逻辑正确性。

因此，本项目不会一开始就把 MCTS 写进模型主体，而是先建立可观察的“模型 + 工具 + 验证器”循环，再把 MCTS 作为测试时搜索器接入。

## 5. 总体系统形态

目标系统可以逐步发展成以下结构：

```text
用户问题
    ↓
小型语言模型：提出问题分解和下一步行动
    ↓
检索器 / 代码执行器 / 规则工具
    ↓
状态记录：保存材料、中间结论和历史轨迹
    ↓
验证器：判断事实、计算或代码结果
    ↓
循环计算或 MCTS：继续扩展、修正、回溯
    ↓
答案合成器：给出结论、依据和不确定性
```

模型内部的循环与外部的 MCTS 应保持清晰的接口。这样可以分别回答两个问题：

- 增加模型自身的计算轮数是否有帮助？
- 在相同模型基础上增加外部搜索是否有帮助？

## 6. 分阶段路线

### 阶段 0：建立可重复的最小框架

目标是先具备可靠的实验环境：

- tokenizer、数据集切分和 batch 采样；
- 训练、验证、checkpoint 保存与恢复；
- loss、困惑度、参数量、吞吐量和显存统计；
- 固定随机种子和实验配置；
- 统一的文本生成和评估脚本；
- 保存每次实验的配置、日志和固定样例。

先用 10M 以内的小配置验证完整流程，再逐步扩大规模。这个阶段不研究新架构，重点是保证之后的结论可以复现。

完成标准：同一配置可以重新启动训练，并得到趋势相近的 loss 曲线和评估结果。

### 阶段 1：标准 Transformer 自回归基线

实现一个标准的 decoder-only Transformer，作为所有实验的共同基线。

固定并记录：

- tokenizer 和词表大小；
- 上下文长度、层数、隐藏维度和头数；
- 优化器、学习率和训练 token 数；
- 参数量、训练速度、显存和验证集困惑度；
- 固定提示词的生成结果。

第一版建议使用 10M～30M 参数。只有基线能够稳定训练，之后的结构比较才有意义。

### 阶段 2：构造“有限知识、强推理”的评估集

开放问答会把知识量、检索能力和推理能力混在一起，不适合用来判断 MCTS 或循环结构是否真正有效。因此需要建立可控的小型评估集。

建议包含：

- 合成规则推理：资料全部提供，但需要组合多条规则；
- 多跳数学题：每一步都可以由验证器检查；
- 小型代码修复：用单元测试判断候选答案；
- 文档多跳问答：答案分散在多份短文档中；
- 弱关联跨领域题：给出两个领域的材料，要求寻找关系并说明边界；
- 反例识别：要求模型证明一个结论不一定成立。

每道题最好保存标准答案、可接受答案、推理步骤或验证规则。评估重点是正确率、验证通过率、平均计算步数和错误类型，而不是只看文本相似度。

### 阶段 3：Mamba 自回归模型

在保持 tokenizer、数据集、训练预算和输出头一致的前提下，用 Mamba 替换 Transformer 的注意力或主要序列建模模块。

优先研究因果 Mamba，因为它与自回归训练目标天然匹配。需要检查：

- 训练时的完整序列计算和推理时的增量状态更新是否一致；
- 长上下文下的 loss、吞吐量和显存变化；
- 相同参数量和相同训练 token 数下的表现；
- Mamba 对需要多步推理的评估集是否有特殊影响。

这一阶段的目的主要是理解序列骨干和工程代价，不要同时引入循环深度、扩散目标或 MCTS。

### 阶段 4：Looped Transformer 和共享权重循环

让一个 block 重复执行多次，并共享其参数：

```text
h = embedding(tokens)

for loop_index in range(num_loops):
    h = shared_block(h, loop_index_embedding)

logits = output_head(norm(h))
```

先比较 1、2、4、8 次固定循环。可以给每次循环加入 step embedding，使模型知道当前处于第几轮。

需要分别比较：

- 普通堆叠 block；
- 共享权重的固定循环；
- 共享权重但加入循环编号 embedding；
- 相同总计算量下的普通堆叠和循环结构。

重点观察循环是否改善合成推理和多跳任务，而不只是降低验证集困惑度。循环次数增加后，必须同时记录推理成本。

### 阶段 5：注意力残差与历史状态读取

在循环结构中保留每一轮的表示，让当前状态能够读取更早的状态：

```text
history = [h]

for loop_index in range(num_loops):
    h = shared_block(h)
    read = attention(query=h, keys=history, values=history)
    h = h + gate * read
    history.append(h)
```

第一版采用门控读取，并限制历史状态数量，避免显存和计算量快速增长。之后再研究历史状态压缩、稀疏读取和只读取关键循环步骤。

对照实验至少包括：

- 普通残差；
- 门控残差；
- 注意力残差；
- 注意力残差但不共享 block 参数。

目标是判断跨循环读取是否真的帮助模型修正和组合信息，而不是把额外参数或额外计算误认为机制收益。

### 阶段 6：建立工具调用和验证器循环

在实现 MCTS 前，先建立一个简单的单路径推理循环：

```text
模型提出行动
  -> 执行检索、计算、代码或规则检查
  -> 将结果写回当前状态
  -> 模型根据新状态提出下一步行动
  -> 达到停止条件后生成答案
```

先使用确定性的工具和验证器：

- 算术和符号计算器；
- Python 代码执行与单元测试；
- 文档检索；
- JSON schema 或规则检查；
- 简单的答案匹配和约束检查。

每个行动都应有明确的输入、输出和失败状态。这样可以观察模型到底是在正确使用工具，还是只是在生成看起来合理的调用文本。

### 阶段 7：Best-of-N 和树搜索

先实现 Best-of-N，再实现 MCTS。Best-of-N 更简单，可以验证“多次尝试 + 验证”是否有效，也能作为 MCTS 的基线。

建议顺序：

1. 单次生成 + 验证；
2. N 次独立生成 + 选择验证得分最高的结果；
3. 按问题步骤生成候选动作；
4. 对候选动作做有限深度树搜索；
5. 加入 MCTS 的选择、扩展、模拟和回溯；
6. 比较 MCTS 与随机搜索、Best-of-N 和束搜索。

MCTS 节点可以保存：

- 当前问题状态；
- 已执行的行动；
- 检索到的材料；
- 中间结论；
- 验证器得分；
- 子节点访问次数和累计价值。

第一版使用固定深度和固定预算，不要一开始实现复杂的自适应停止。搜索预算应该作为显式变量，例如 16、64、256 次节点扩展。

### 阶段 8：扩散语言模型基线

在理解自回归模型和外部搜索之后，再实现扩散语言模型。先用 Transformer 作为去噪器，单独验证训练目标和采样流程。

记录以下变量：

- token 掩码或离散噪声的定义；
- 噪声强度和时间步采样方式；
- 时间步 embedding 的注入位置；
- 损失函数和被预测 token 的范围；
- 采样步数与质量、速度的关系。

扩散去噪通常需要双向上下文，而标准因果 Mamba 只能使用左侧上下文。因此不能直接把因果 Mamba 替换到扩散模型中并期待结构自然成立。后续可以比较双向 Mamba、Mamba/Attention 混合去噪器和 Looped 去噪器。

### 阶段 9：组合实验

只有单项机制都能独立工作后，才开始组合。推荐顺序如下：

```text
自回归 Transformer
  -> 自回归 Mamba
  -> Looped Mamba
  -> Looped Mamba + 注意力残差
  -> Looped Mamba + 工具验证
  -> Looped Mamba + Best-of-N / MCTS
  -> 扩散 Transformer
  -> 扩散 Looped Transformer
  -> 扩散双向 Mamba/Attention 混合结构
```

最终候选系统可以是：

```text
有限规模语言模型
  ├── Mamba 或 Mamba/Attention 序列骨干
  ├── 共享权重循环，提供额外内部计算
  ├── 注意力残差，读取历史中间状态
  ├── 检索和工具调用，补充外部知识
  └── 验证器 + MCTS，选择和修正推理路径
```

这个组合不是一次性模型设计，而是一组可以拆开测量的组件。每次实验只增加一个主要变量，并保留之前最好的模型作为对照。

## 7. 规模与计算预算

0.1B 参数可以作为阶段性目标，但不适合作为每次实验的起点。建议使用三级规模：

| 规模 | 用途 | 主要问题 |
| --- | --- | --- |
| 5M～10M | 代码和算法调试 | forward、反向传播、状态和采样是否正确 |
| 20M～50M | 结构筛选 | 哪种机制值得继续投入计算 |
| 约 100M | 阶段结论 | 结论在目标规模下是否仍然成立 |

外部搜索还需要单独记录测试时预算。模型大小相同并不代表系统成本相同，应同时报告：

- 单次模型前向次数；
- 搜索节点数和最大深度；
- 检索次数与工具调用次数；
- 总延迟和显存；
- 正确率提升对应的额外计算量。

判断“更聪明”时，应该比较质量与计算成本的关系，而不是只比较最高分。

## 8. 统一评估方法

每个模型至少进行四类评估：

1. 语言建模：训练 loss、验证 loss 和困惑度。
2. 受控推理：规则、多跳数学、代码修复和文档多跳任务。
3. 检索与工具使用：调用准确率、引用材料是否被正确使用、验证器通过率。
4. 效率：参数量、吞吐量、显存、延迟和总推理计算量。

核心对照应保持为：

```text
同一模型、同一材料
  -> 单次推理
  -> 多轮循环推理
  -> 多候选推理
  -> 多候选推理 + 验证
  -> MCTS + 验证
```

如果材料已经提供，而循环或搜索仍然不能提高正确率，说明问题可能在状态表示、评分器或行动接口，而不是知识规模不足。

## 9. 每次实验的记录格式

每个实验目录保存配置、日志、评估结果和固定样例，至少记录：

- 实验名称、日期和代码版本；
- tokenizer、数据集和评估集版本；
- 参数量、训练 token 数和训练步数；
- batch size、学习率、优化器和学习率策略；
- 层数、隐藏维度、上下文长度和循环次数；
- 搜索预算、节点深度、工具和验证器配置；
- 训练 loss、验证 loss、任务正确率和验证通过率；
- 吞吐量、显存峰值、平均延迟和总推理成本；
- 与哪个基线比较；
- 观察到的错误、结论和下一步问题。

建议每个实验只回答一个主要问题。例如：“在相同总计算量下，4 次共享循环是否优于普通 4 层堆叠？”比“这个复杂结构是否更聪明？”更容易得到可靠结论。

## 11. 第一阶段完成标准

进入复杂组合实验前，至少满足以下条件：

- Transformer 基线可以稳定训练和生成；
- Mamba 版本可以完成训练和增量推理；
- 共享权重循环可以反向传播，循环次数可配置；
- 历史状态读取不会破坏训练稳定性；
- 受控推理评估集可以自动评分；
- 至少有一个确定性工具和一个可靠验证器；
- Best-of-N 可以运行并与单次推理比较；
- 所有实验都能保存配置并复现；
- 参数量、训练成本和测试时搜索成本可以分别统计。

## 12. 最终要回答的问题

SmallNeko 最终不只是比较 Transformer 和 Mamba 的困惑度，而是希望回答以下问题：

> 对于知识量有限的小模型，增加内部循环、历史状态读取、工具调用和测试时搜索，能否在受控的弱关联、多跳和跨领域任务上获得可测量的推理收益？这种收益是否足以抵消额外的训练和推理成本？

如果答案是肯定的，下一步才值得研究更复杂的扩散去噪器、双向 Mamba、动态循环次数和更高效的树搜索。如果答案是否定的，也能通过受控实验定位瓶颈是在知识来源、状态表示、验证器、搜索策略还是模型骨干。
